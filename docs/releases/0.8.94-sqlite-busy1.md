# PalPanel 0.8.94 sqlite-busy1

## 问题

后台日志周期性出现：

```text
crash guard observation failed: database is locked (5) (SQLITE_BUSY)
```

该日志表示 crash guard 的本次观测没有完成，不表示 PalServer 已崩溃，也不表示 SQLite 文件已经损坏。

## 根因

crash guard 默认每 5 秒执行一次。旧实现即使运行模式、容器状态、重启计数和生命周期签名完全没有变化，也会更新 `crash_guard_state` 单例行。面板中的任务、事件桥接、商城、Boss 和存档模块使用同一个 SQLite 数据库；当其他模块持有较长写事务时，这个无意义的周期写入会等待到 SQLite `busy_timeout` 到期并返回 `SQLITE_BUSY`。

## 修复

- 服务器状态没有变化且没有新崩溃事件时，只读取状态，不再写入 SQLite。
- crash guard 必要的状态读取、状态写入、事件写入、事件清理和计数查询增加 4 次分阶段锁重试。
- 重试间隔为 100ms、250ms、500ms；每次数据库调用仍保留 SQLite 自身的锁等待。
- 重试尊重进程关闭和请求取消，不会阻塞关机。
- 错误日志现在标明失败阶段，例如 `write crash guard state` 或 `record crash guard event`。
- 如果状态行已更新但崩溃事件最终无法写入，会恢复旧状态签名，确保下一次观测仍能重新识别该崩溃，不会静默漏记。
- 不修改数据库结构，不需要迁移数据。

## 部署

1. 备份面板 SQLite 数据库。
2. 将增量包解压到仓库根目录并覆盖同名文件。
3. 重新构建后端。
4. 重启面板。

不要在面板运行时删除 SQLite 的 `-wal` 或 `-shm` 文件。

## 验证建议

重启后观察 30 分钟以上：

- 正常稳定运行时，不应继续出现原来的无阶段 `database is locked` 日志。
- 如果存在持续超过所有重试窗口的外部写锁，日志会保留，但会带有明确操作阶段，便于继续定位具体竞争点。
- Crash Guard 页面中的状态和历史事件应保持正常。
